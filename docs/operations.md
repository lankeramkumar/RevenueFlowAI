# Operations

Status: covers the local/demo Compose deployment actually built and
verified. This is not a production runbook — see "Production gates" at
the end for what's missing before any real deployment.

## Deployment (local/demo)

```bash
cd infra
docker compose up --build
```

Services: `db` (Postgres 16), `localstack` (S3-compatible storage),
`keycloak` (OIDC), `backend` (FastAPI), `worker` (import processor),
`frontend` (Vite/React, served via `serve`). All six report healthy on a
clean start — verified repeatedly throughout this build.

**Host ports**: frontend 5173, backend 8000, Keycloak 8080, LocalStack
4566, Postgres **5433** (not the default 5432 — a pre-existing native
Postgres service on the build machine held 5432; see README's
troubleshooting section).

## Migrations

Alembic manages schema; the backend container runs `alembic upgrade head`
automatically on startup (see `infra/Dockerfile.backend`'s `CMD`). To run
manually:

```bash
cd backend
.venv\Scripts\python.exe -m alembic upgrade head   # apply
.venv\Scripts\python.exe -m alembic downgrade -1   # roll back one revision
.venv\Scripts\python.exe -m alembic history         # list revisions
```

Every migration in this repo was either hand-written and verified to
compile against the Postgres dialect offline, or autogenerated against a
live database and applied for real — never applied blind. Each migration
has a corresponding `downgrade()`.

## Health and readiness

- `GET /healthz` — liveness, no dependencies, no auth.
- `GET /readyz` — readiness, executes `SELECT 1` against Postgres.

Both are wired into the backend container's Docker healthcheck.

## Worker recovery

The worker claims jobs via `SELECT ... FOR UPDATE SKIP LOCKED` with a
5-minute lease (`worker.py`). A crashed worker's lease expires and another
worker instance (or the same one restarted) can reclaim the job; attempts
are capped at `MAX_ATTEMPTS = 5`. **This mechanism is implemented but not
yet exercised by an automated test** that actually kills a worker
mid-job and confirms recovery — tracked as a Milestone 6 gap. Manual
verification during this build confirmed normal (non-crash) job
processing end-to-end repeatedly.

## Logging

Backend and worker use `structlog` for structured log lines (see
`import_job.processed`, `worker.started` log events in `worker.py`).
**Not yet implemented**: correlation/trace IDs threaded through a
request, metrics export (job latency, tool latency, token usage), or log
redaction policy for sensitive fields — all tracked gaps.

## Retention and rollback

`DatasetVersion` rows are never deleted on activation — the previous
active version is marked `is_active=False` with a `superseded_at`
timestamp, not removed. This means:
- Rollback to a previous dataset version is a data operation (flip
  `is_active` back), not yet exposed as an API/UI action.
- No retention/cleanup policy exists yet for old `ImportJobFile` objects
  in the object store or old `DatasetVersion` rows in Postgres — both
  accumulate indefinitely today. A documented retention policy is a
  Milestone 6 gap.

## Backup and restore

**Not implemented or drilled.** For the local Compose setup, Postgres
data lives in the `db-data` named volume and LocalStack data in
`localstack-data` — a `docker volume` backup of both, taken while the
stack is stopped for consistency, would be the starting point, but this
has not been tested as an actual restore procedure. A real backup/restore
drill is a documented production gate (see below), not something this
build claims to have verified.

## Secrets and configuration

All configuration is environment-variable-driven (`config.py`'s
`Settings`, sourced from `.env` / Compose `environment:` blocks). No
secret is hardcoded. See `docs/security.md` for the full secrets posture.

## Current operating procedures (2026-10-03)

**First start.** `docker compose up --build` in `infra/` starts Postgres,
LocalStack, Keycloak, the backend (applies migrations), the worker, the
frontend, and a one-shot `demo-seed` that creates the demo organization and
activates the demo dataset. It is idempotent: if the admin email already has
an account, it does nothing.

**First tenant in a real deployment.** Run
`python -m revenueflowai.bootstrap --org-name ... --org-slug ... --admin-email ...`.
The admin account is created pending and bound to the Keycloak identity on
first sign-in, but only when Keycloak reports the email as verified.

**Health and metrics.** `/healthz` (liveness), `/readyz` (database check),
`/metrics` (Prometheus text, unauthenticated). Restrict `/metrics` to the
internal network at the ingress; it is not behind authentication.

**Logs.** JSON in any environment other than `development`. Correlate by
`request_id`, which is also returned in the `X-Request-ID` response header.

**Quality gate.** `python -m revenueflowai.evals --organization-id ...
--business-unit-id ... --actor-user-id ...` exits 1 below 100% pass rate or
citation validity. Add `--live` to run the Anthropic planner (spends tokens).

**Backups and restore.** Not yet exercised. A restore drill is an open
production gate.

## Added 2026-10-03

- **Worker metrics.** The import worker serves Prometheus-format metrics on
  port 9100 (`WORKER_METRICS_PORT` to change it): `import_jobs_claimed_total`,
  `import_jobs_total{outcome}`, and `import_job_duration_seconds`. Compose publishes
  9100 on the host; restrict it at the network edge as for the backend.
- **Document storage.** Uploaded files are kept in the `documents` bucket
  (`S3_BUCKET_DOCUMENTS`). The bucket is created at API startup. Uploads are limited
  to 10 MB and to UTF-8 text or PDF, and every upload is written to the audit log.
- **Investigation budgets.** At most 3 specialist dispatches and 20 seconds per
  investigation by default. An answer that hits a limit says so in its missing-data list.
